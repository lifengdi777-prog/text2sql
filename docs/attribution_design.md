# 归因分析(attribution)设计说明 · MVP

> 面向 Excel 数据集(dataset_agent 的能力扩展):回答"**为什么变了 / 差在哪**",而不只是"是多少"。
> 触发方式:**用户跑完一条普通查询、看到结果后,点「归因分析」按钮**(不靠用户问疑问句)。
> 核心一句话:**归因 = 会计式拆账**——把一笔"总变化/总差异"按维度拆到每一项,SQL 算账、LLM 说人话。

---

## 1. 这不是机器学习,是算术分解

全部秘密就一句:**总数 = 各部分之和,所以"总变化 = 各部分变化之和"**。

例:销售额 120万 → 100万(跌 20万)。按地区拆(一条 SQL):

| 地区 | 上月 | 本月 | 变化 | 贡献度 = 变化/总变化(-20) |
|---|---|---|---|---|
| 华南 | 50 | 32 | **-18** | **90%** |
| 华东 | 40 | 38 | -2 | 10% |
| 华北 | 30 | 30 | 0 | 0% |

各地区变化加起来 = 总变化 ✓ → "90% 是华南拖累的"。纯减法+除法,**无模型、无训练、无 ML**,数字张张可复核。

> 边界:这是**贡献度分解,不是统计因果**。要"自动找未知驱动因素 / 因果"才需要 ML(Key Influencers / 因果推断),不在 MVP 内。

---

## 2. 触发:按钮流(不需要用户问"为什么")

用户照常查数 → 看到异常 → 点「归因分析」。系统**解析他刚跑的那条 SQL + 结果**,自动推出归因要素:

| 要素 | 从哪来(纯代码解析,无需 LLM) |
|---|---|
| **指标** | 查询的聚合表达式 → `SUM(不良数)` 得指标=不良数 |
| **对比轴** | 查询的 `GROUP BY` 列:是**时间列**→ 环比/同比;是**维度**→ 组间对比;无分组→ 看整体 |
| **候选维度** | 表里**其它**低基数分类列(没被当对比轴的那些),自动来自 schema 画像 |

LLM 在归因里只剩**最后一步"说人话"**(把算好的数字组织成结论)。

---

## 3. 归因可用性判断(gate):哪些查询才出「归因」按钮

**不是所有查询都能归因**,点击前先用一个确定性判断决定按钮出不出(解析刚跑的 SQL + 看 schema,零 LLM):

**出按钮的条件 = 有可加总的指标 + 有可对比或可拆的轴**,即同时满足:
1. **有聚合指标**:SELECT 里有 `SUM/COUNT/AVG(...)`(纯明细 `SELECT *` → 不出)。
2. **有可对比/可拆的轴**:表里有**时间列**(能环比/同比)**或**还有没被用作对比轴的**分类列**(能按维度拆)。

| 用户刚跑的查询 | 出「归因」? | 原因 |
|---|---|---|
| 各月销售额 / 各产线不良数 | ✅ 出 | 有聚合 + 有维度/时间可拆 |
| 总销售额(单个数,但表里有时间或其它维度) | ✅ 出 | 能按时间环比、或按维度拆 |
| 列出所有订单 / `SELECT *` 明细 | ❌ 不出 | 无聚合指标,无可拆 |
| 查某条记录 / 某个值 | ❌ 不出 | 单条记录,无总量概念 |
| 已拆到最细、又无时间无其它维度 | ⚪ 灰掉 | 没有可继续拆的轴 |

判断三连(全确定性):**有聚合? → 有时间列? → 有剩余分类维度?** 满足"有聚合 + (有时间 或 有维度)"就亮按钮。

### 前置查询 → 归因类型(出按钮后,做哪种归因)

归因分两大模式,由**用户刚跑的那条查询的形状**自动决定(解析 SQL,不用 LLM):
- **变化归因(为什么变了)**:查询里有时间或能比两组 → 需要对比基准
- **构成归因(谁是大头/谁异常)**:查询按维度分组、无时间 → 直接拆水平

| 前置查询 | 归因类型 | 例子 |
|---|---|---|
| **按时间分组**(各月/各周 指标) | **变化归因**:取最近两期(环比,可切同比),按其它维度拆贡献度 | "各月销售额" → 10月为何比9月跌 |
| **按维度分组**(各X 指标,无时间) | **构成归因**:谁是大头(帕累托)/ 谁异常 | "各产线不良数" → 集中在 L2 |
| **单个汇总数**(无分组) | 有时间列 → 转最近两期变化归因;无时间 → 按维度拆构成 | "总销售额" → 按月环比 / 拆地区 |
| **时间 × 维度交叉**(各月各X) | 变化归因增强:锁定变化期 + 多维一起拆 | "各月各品类销售额" |

**两点横切**(叠加在以上任意一种):
- 指标是**率/均值** → 改拆它的分子量(见 §5 指标范围)。
- **明细 / 无聚合**(`SELECT *`)→ gate 直接不出按钮。

判定规则(解析 SQL):有 `SUM/COUNT/AVG`? `GROUP BY` 是时间列/维度/无/时间+维度? 指标是不是 `SUM(a)/SUM(b)` 的率? → 自动归到上表某行。**最常见的是前两行**(各月X → 变化归因;各维度X → 构成归因)。

## 4. 整体流程

```
用户跑普通查询 "各月不良数" → 看到 4 月暴涨 → 点「归因分析」
  ↓
gate 判断:有 SUM(不良数) + 有时间列(月份)+ 有其它维度 → 出按钮 ✅
  ↓
① 解析旧查询(代码):指标=不良数;对比轴=月份(时间)→ 取最近两期;候选维度=[产线,缺陷类型,班次]
  ↓
② decompose(并行):对每个候选维度套同一个模板,生成 N 条 SQL,DuckDB 同时跑
  ↓
③ rank(代码):按"解释力(集中度=单成员最大贡献度)"给各维度排序,挑主因维度
  ↓
④ interpret(LLM):把数字说成结论 + 一句可执行建议
```

## 5. 模板:MVP 只做 1 个(维度贡献度 / 加法)

**主力模板就一个**,单独就能回答"哪个维度、哪个成员贡献最大",覆盖 80%+ 场景——任何能 SUM 的指标(销售额、不良数、产量、订单量…)都用它:

```sql
-- 维度贡献度模板(空:表名、指标、维度、时间列、两期值)
WITH cur  AS (SELECT {维度} k, SUM({指标}) m FROM "{表}" WHERE {时间列}={本期} GROUP BY {维度}),
     prev AS (SELECT {维度} k, SUM({指标}) m FROM "{表}" WHERE {时间列}={上期} GROUP BY {维度})
SELECT COALESCE(cur.k,prev.k) AS 成员,
       COALESCE(prev.m,0) AS 上期, COALESCE(cur.m,0) AS 本期,
       COALESCE(cur.m,0)-COALESCE(prev.m,0) AS 变化,
       (COALESCE(cur.m,0)-COALESCE(prev.m,0))/NULLIF({总变化},0) AS 贡献度
FROM cur FULL JOIN prev ON cur.k=prev.k ORDER BY ABS(变化) DESC
```

"对每个维度套模板" = 只换 `{维度}` 这个空,生成 N 条具体 SQL **并行跑**:

| 维度 | 生成的 SQL(仅 `{维度}` 不同) |
|---|---|
| 产线 | `… SUM(不良数) … GROUP BY 产线 …` |
| 缺陷类型 | `… SUM(不良数) … GROUP BY 缺陷类型 …` |

**填空来源**:`{表}{指标}{时间列}{两期}` 来自解析旧查询;`{维度}` 来自 schema 的分类列(挨个填)。**LLM 不写 SQL 逻辑,只在最后说人话。**

### 解释力排序(挑主因,数字说话)
每个维度算完后打分 = **单成员最大贡献度(集中度)**:某维度一拆,变化几乎全压在一两个成员上 → 它最能解释。按分数排序,取前几个维度作主因。
> 注:低基数维度(如二值"是否会员")天然容易"集中",用集中度会偏高——更严谨要用惊奇度(Adtributor)归一化,属后续增强,**仍非 ML**。

### 可归因的指标范围(MVP)
加法模板的前提是指标**可加总(总量 = 各部分之和)**,所以:

| | 指标 | 能否归因 |
|---|---|---|
| ✅ **可加总的量** | 销售额、销量/数量、产量、不良数、订单数(COUNT)、成本、利润额、库存量、工时、停机时长、退货量… | **能**,加法模板直接拆 |
| ⚠️ **率/均值/客单价**(分子÷分母 或 平均) | 良率、达成率、不良率、毛利率、客单价、件单价 | **率本身不可加**(各组的率加起来 ≠ 总率),MVP 不直接拆;但可退一步**拆它的分子量**(拆"不良数"而非"不良率"),实践常够用 |
| ❌ **极值/分位** | MAX、MIN、中位数 | 无法有意义分解 |

> **MVP 能归因所有"可加总的量"(sum/count)**;率和均值先拆它的分子量,精确拆率靠后续模板。
> 小坑:`COUNT(DISTINCT 客户ID)` 按维度拆是**近似**(同一客户可能跨组),解读需谨慎。

### 后续可选(MVP 不做)
指标有内部结构时,再额外加一层拆解(**只是锦上添花,核心结论靠加法模板**):
- 量价分解(指标=数量×单价 → 是量跌还是价跌)
- 比率分解(率=分子/分母 → 精确拆率本身的变化)
- 乘积链(OEE=可用率×性能×良率)

## 6. 实战 walkthrough(制造业,真实跑通)

数据「生产明细」:不良数 **3月 200 → 4月 360(+80%)**。用户先查"各月不良数",点归因:

按产线拆 → **L2:80→220,+140,贡献 87.5%**;L1/L3 各 +10。
按缺陷类型拆 → **焊接不良:40→182,+142,贡献 88.8%**;其余合计 +18。
按班次拆 → 白班 +80、夜班 +80,平摊(各 50%)。

解释力排序:`缺陷类型(89%) ≈ 产线(88%) ≫ 班次(50%)` → 主因是 **L2 产线的焊接不良**。

LLM 解读:
> "4 月不良数环比涨 80%。**主因高度集中在 L2 产线的焊接不良**(各贡献约 88%),白/夜班都涨说明不是班次问题——建议优先排查 L2 焊接工序/设备。"

(销售同理:销售额环比下滑 → 按地区/品类/是否会员拆,自动找主因。)

## 7. 跨行业怎么通用

模板填的是**"角色"(一个指标、一个维度、一个时间),与行业无关**;制造只是列名不同:

| 空位 | 销售 | 制造 |
|---|---|---|
| {表} | 订单明细 | 生产明细 |
| {指标} | 金额 | 不良数 / 产量 |
| {维度} | 地区 / 品类 | 产线 / 缺陷类型 / 班次 |
| {时间列} | 月份 | 日期 / 周 |

- **哪些列能当指标/维度/时间**:入库时 schema 画像已自动分好(numeric/categorical/temporal),**任何行业的 Excel 都一样工作**。
- **优雅降级(绝不翻车)**:没有时间列 → 改"A组 vs B组"对比归因;高基数列(商品名称/客户ID)→ 自动跳过全维扫描或只看 Top-N。

## 8. 对比基准:环比 / 同比 / 自定义(可用性 + 默认 + 降级)

三种对比**共用同一个加法模板,只换 WHERE 的两个时间值**,不增加模板。

**① 可用性 —— 看数据自动判**

| 对比 | 可用条件 | 否则 |
|---|---|---|
| **环比** | 时间列有 ≥2 个相邻期(几乎恒满足) | —— |
| **同比** | 时间列**跨 ≥2 年**且**去年同期真实存在**(本期 `2025-04`,数据里有 `2024-04`) | **选项置灰/隐藏** |
| **自定义 / A vs B** | 总可用 | —— |

> 判"去年同期存在":时间列若是月粒度(`2025-04`),解析出年/月,查数据里有没有 `2024-04`;有才点亮同比。

**② 默认 —— 固定环比**(最近一期 vs 上一期)。即使同比可用,也默认环比;同比由用户**主动切**。若用户当前已在看某个对比(如卡片显示环比),则**继承**它。

**③ 取哪两期**:多期结果默认"**最新期 vs 前一期**";想看别的转折,用切换器或点图选任意两期。

**④ 没有时间列 → 降级**:不显示环比/同比,改为"**对比两组(A vs B)**"或"**帕累托**(拆总量构成,不做变化归因)"。

**例**(你的销售数据只覆盖 2025 一年):没有去年同期 → **同比置灰**,默认 9→10 月环比;哪天补上 2024 年数据,同比**自动点亮**,无需改代码。

> 不强制用户每次先选:**默认环比直接出结果**,需要看季节性再切同比。

## 9. MVP 落地范围

**直接复用 dataset_agent 现有能力**:load_schema(列+语义类型)、DuckDB 执行、interpret_result(已强化防幻觉+制造/销售用词)。

**MVP 要新增**:
- 「归因」按钮的**可用性判断(gate)**(解析旧 SQL + schema,确定性)
- 解析旧查询取槽位(指标/对比轴/候选维度)
- **1 个加法贡献度模板** + 并行跑 + 集中度排序
- 1 个归因解读 prompt

**MVP 不做**:量价/比率/乘积链三模板、Adtributor 根因搜索、瀑布图。后续按需加。

> 复杂度:中等偏低。核心就"gate + 解析旧查询 + 一个模板填空并行跑 + 排序 + 解读",约 1 天可跑通。

## 10. PPT 话术

> 从"看数"升级到"**解释为什么**"。用户查出 4 月不良数暴涨,点一下「归因」,
> 系统自动把这笔增长拆到各维度,一句话给出主因:"**主因 L2 产线的焊接不良,贡献约 88%**"——
> 全程算术拆账,数字可追溯、可复核,不是黑盒。
